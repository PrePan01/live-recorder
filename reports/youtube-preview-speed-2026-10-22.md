# YouTube 预览启动优化（2026-10-22）

## 定位与实施

复查并测量平台解析、音视频清单、初始分片、原始媒体与预览交付。沿用原始画质、编码及同源录像/预览机制，没有扩大元信息缓存有效期或引入无人观看时的常驻取流。

1. **初始分片渐进交付。** 原预取必须等整个分片读完才向 FFmpeg 返回，首部可用时仍等待尾部。现在使用 PassThrough 按背压交付已到达字节；未消费的预取 10 秒后取消，最多 4 个，每个读写侧高水位 1 MiB。高水位并非进程内存硬上限，网络缓冲与当前数据块另计。大分片沿同一请求流式传输，不再读满上限后丢弃并重新下载。失败发生在交付前仍走按需重试；消费者断开会取消已认领请求。
2. **缩短已知媒体的本地预览探测。** 仅 YouTube 的 Matroska→FLV 预览进程，将分析预算从 1 秒改为 100 毫秒，探测字节上限从 1 MiB 改为 256 KiB，关闭额外帧率估算。此输入已有本机生成的完整轨道和编码配置，转码预览仍显式输出 30 fps；上游网络输入的探测策略保持原样。分析预算是上限，并不是固定等待时间，不能据此宣称每次节省 900 毫秒。
3. **移除 YouTube 播放器的字节门槛。** 原播放器收到预览后，还先累计 128 KiB 才向解复用器交付。YouTube 现在直接交付首包，仍由解析器保留不完整标签，MSE 保留正常播放缓冲和轻微加速追赶。普通预览、缩略预览均传递平台标识；其他平台维持原配置。

测试明确覆盖“首包到达、分片尾部尚未返回”时就能读取媒体，以及消费中断、响应前/响应体失败、范围请求和大分片。前端通过当前安装的 mpegts 实际 I/O 控制器验证小首包即时交付及不完整标签保留，没有在测试中重写该缓冲算法。

## 实测口径

以下全部为公开直播 `rFZHOHl-L8A`、720p、匿名独立临时文件。从开始请求适配器计时到**后端首媒体事件**，不是屏幕首帧。独立应用测试使用隔离数据库，不操作用户当前录制。

| 样本 | 平台解析 | 首预览数据 | 解析后至首预览 |
| --- | ---: | ---: | ---: |
| 最早基线，独立进程冷预览 | 6.668 秒 | 10.055 秒 | 3.387 秒 |
| 修改后，独立进程冷预览 | 3.809 秒 | 7.194 秒 | 3.385 秒 |
| 修改后，冷录制同时预览 | 3.792 秒 | 7.095 秒 | 3.303 秒 |
| 修改后，同进程解析缓存命中的预览 | 0 秒 | 2.038 秒 | 2.038 秒 |

每行是一次短时运行。冷启动前后差值几乎都来自平台解析波动，**不能用 10.055→7.194 秒宣称优化带来约 28% 的固定收益**。这轮去掉了可证明的不必要整段/字节门槛；对本直播尚无稳定冷启动显著提速的证据，余下主要等待仍在平台解析和上游网络。

同一次真实网络轨迹交给新旧 mpegts I/O 策略回放，本样本首包本来就大于旧门槛，两者都立即交付，节省为 **0 毫秒**，见 [配对回放](youtube-preview-buffer-comparison.json)。这与小首包回归不矛盾：不能把小首包时消除的等待推广为每条直播的固定收益。

流式预取的一次最终样本中，原生媒体在 7.015 秒开始交付，首批分片完整读取在 7.101 秒结束，预览在 7.095 秒开始交付。另一轮原生媒体 6.634 秒、分片结束 6.943 秒，证明新路径不再强制等待整段结束；这些阶段顺序不能单独用于估算屏幕提速。

尝试跳过网页/配置解析的一组实验失败，跳过 initial_data 的样本也未显示改善，均未写入生产配置。完整原始测量见 [样本与数据包时间轨迹](youtube-preview-speed-samples.jsonl)。

复现命令：

```sh
npm --prefix backend run build
node backend/scripts/youtube-startup-benchmark.mjs 'https://www.youtube.com/watch?v=rFZHOHl-L8A' cold 720p preview > /tmp/youtube-preview.log
node frontend/scripts/benchmark-preview-buffer.mjs /tmp/youtube-preview.log
```
