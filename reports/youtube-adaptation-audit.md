# YouTube 适配排查与修复（2026-10-22）

## 排查范围

检查当前工作区 YouTube 专用实现，以及关联的前后端接入差异：URL/频道解析、画质与媒体来源选择、系统代理、Cookie、聊天采集、录制与预览生命周期、Matroska 时钟、分段与暂存恢复、回看和片段快照、历史重命名/后处理/上传入口、迁移与设置、界面平台识别、运行时打包和校验。

本次保留工作区已有适配，针对下面列出的可复现问题修正；不把此前报告中的真实直播验收视为本轮验收。

## 根因及修复

| 问题 | 根因 | 修复与证据 |
| --- | --- | --- |
| 媒体轨道几秒一跳 | HLS 分片成批到达，媒体尾部按批更新；界面直接显示媒体尾部 | YouTube 录制中的媒体轨道按正常速度消费已确认媒体。轨道与直播标记沿用同一个显示值，不越过后端已收到的尾部；耗尽后冻结、停止后显示最终时长。假时钟覆盖突增、停滞、隐藏页面及切换录制。录制会话计时采用下文的独立修复。 |
| 关闭再打开预览不出帧、混入旧数据 | 旧进程被杀后仍占据当前预览引用，其输出队列也可能在新预览打开后继续交付 | 关闭时立即释放当前引用并推进代次；过滤旧进程输出与已排队事件。真实 FFmpeg 回归在上游暂停期间完成开启、立即关闭重开、取得关键帧并实际解码。 |
| 硬件预览失败后等下一分片才回退 | 失败只标记后续启动走软件编码，未主动重启 | 保留已确认关键帧组，硬件失败时立即启动软件回退。测试强制硬件启动报错，验证没有新分片也能出帧和重开。 |
| HLS 预取暂时失败导致起流失败 | 预取 Promise 的拒绝直接变成解码器请求的 HTTP 502 | 预取失败后按需重新请求，保留原有超时和取消机制。回归验证首次预取失败、后续请求成功。 |
| 重启后续录分段的暂存未恢复 | 活跃录像恢复只补写原始路径，续录写入器的暂存属于 `.part-N.mkv` | 按已验证清单先恢复所有分段，再判断媒体是否存在；历史分段恢复后的大小按总文件集合计算。回归覆盖原始文件不存在、有效媒体全部在续录暂存中的场景。 |
| 回看快照仍依赖原始路径 | 已固定媒体 inode，编码探测却再次打开原始录像路径 | 从同一个固定快照/继承句柄读取媒体头；删除原路径后，头部探测与 FFmpeg 读取均通过，覆盖硬链接和无硬链接卷。 |
| 新直播录制时旧录像无法后处理或正确重命名 | 使用房间是否在录制，代替目标录像是否在录制 | 按目标录像状态判断。API 回归覆盖房间正在录制时，旧录像启动/重试后处理及实际文件重命名；当前录像仍拒绝处理。 |
| YouTube 链接被识别成其他平台 | 在整个 URL 上先匹配 `bilibili.com`/`douyin.com` | 统一按 URL 主机识别；频道名或查询参数包含其他平台域名时仍识别为 YouTube。 |

显示平滑使用已确认媒体作为上限，因此会保留一个分片量级的显示延迟；不会为了让数字持续变化而在断流后推算不存在的媒体。后台原始媒体位置仍供服务端范围校验使用。

## 后续修正：轨道与停止按钮必须使用同一时钟

上一轮为解决预览加载时的计时停留，将停止按钮单独改成了按 `activeRecording.startedAt` 计算的会话时长，轨道仍按媒体时长显示。这导致按钮与轨道不一致，该方案已撤销。

现在按钮与轨道统一读取 `mediaClock.durationSeconds`（同一个 `trackElapsedSeconds`），移除独立的会话计时组件。标记、回看与导出仍使用媒体范围。监控总览的会话耗时是另一种统计口径，不代替录像的媒体时间。

媒体时钟持续轮询录制进度，不等待播放器 `loadeddata` 或可播放帧。新增回归覆盖播放器 `readyState=0`、录制媒体持续到达时共享时钟逐秒推进，以及替换预览元素后保留媒体位置。若上游没有新媒体，按钮与轨道共同停留在已确认的媒体范围，不用会话耗时虚构可回看内容。

上述为上一轮时钟修正；最新一轮全链路复查与验证见下文。

| 问题 | 根因与修复 | 验证 |

| 跳播等待期间按旧画面打标，旧错误污染新源 | `FilePlaybackClock` 同步失效旧源，按代次/元素身份接受新画面；位置就绪前禁用打标 | 组件测试覆盖旧帧、旧 canplay、旧错误；新源进度/标记/弹幕一致 |

## 验证边界

### 用户再次反馈：先开录、再开预览时计时停到画面加载完成

继续排查发现上一轮遗漏了平滑时钟的首次采样边界：弹窗首次挂载时直接把显示值设为已收到的媒体尾部，没有留下可消费余量。YouTube 下一批分片到来前尾部不变，显示值被上限限制，于是看起来随首帧加载一起冻结。上一轮测试在打开后立即增加模拟媒体尾部，因此未复现这个初始平台期。

本次只读采样当前开发实例，媒体位置接口耗时约 1–5 毫秒，媒体位置会连续数秒相同，再批量增加；没有把该现象归因于等待播放器 readyState。

修复：YouTube 平滑时钟首次采样保留最多 5 秒已确认媒体余量，轨道与停止按钮仍共用同一显示值。缓存最近已提交的显示位置，关闭重开不能使时间倒退。断流耗尽余量后仍在已确认尾部冻结，刚开录没有媒体时不会用会话耗时虚构文件时长。停止后显示完整媒体时长。新增测试覆盖尾部不变且 readyState=0 时逐秒推进、后续分片到达、缓冲耗尽及关闭重开。
