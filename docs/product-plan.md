# Live Recorder 产品方案（MVP）

> 评审状态：✅ 评审通过（2026-08-28），可进入阶段 B 开发

## 1. 产品定义

### 1.1 一句话目标

让用户在自己的 macOS 或 Windows 电脑上，持续关注指定的抖音/B站直播间；直播开始时自动录制到本机指定目录，并在关键事件发生时获得邮件通知。

### 1.2 用户与核心场景

首期服务于单机、单用户的直播内容收藏/留存需求。用户不必守在电脑前或打开浏览器：本地录制服务常驻运行，定期检测已关注房间，发现开播后启动录制。

### 1.3 MVP 成功标准

1. 用户能在首次配置后添加并启用一个有效的 B站或抖音直播间链接。
2. 直播开播后，系统只创建一条录制任务并将文件可靠写入本机目录。
3. 浏览器关闭、录制服务重启后，已启用房间仍会被继续监控。
4. 用户能在 Web 控制台看见状态、历史、文件路径及失败原因。
5. 录制成功启动、最终失败或空间不足时，系统可发送去重后的邮件通知。

## 2. 范围与边界

### P0：本次交付

- 平台：抖音、B站。
- 运行形态：本机常驻录制服务（Node.js 后台进程） + 浏览器访问的 localhost Web 控制台（SPA）；目标系统为 macOS、Windows。
- 直播间：用户手动粘贴链接，支持添加、编辑、启用、停用、删除；拒绝重复、失效及不支持的链接。
- 录制：开播自动录制、断流重连、服务重启后恢复监控、单房间同一场直播不重复录制。
- 本地文件：首次设置保存目录；按平台/主播/开播时间组织文件；保留历史记录、文件路径、大小、开始/结束时间及失败原因。
- 通知：SMTP 邮件；录制实际成功启动、最终失败、磁盘空间不足时通知；同一房间同类事件在去重窗口内只通知一次。
- 页面观看直播：录制中的房间可在监控总览页面实时观看直播画面（flv.js + WebSocket-FLV，最多 2 路同时预览，延迟 < 5 秒）。
- 录制清晰度：用户可在设置中选择默认录制清晰度（原画/1080p/720p/360p），默认原画；若指定清晰度不可用，降级到次高清晰度并记录告警。
- 管理界面：首次设置、直播间管理、监控总览、录制历史、设置与告警。
- 可测试性：平台检测器、录制器、磁盘/文件系统、SMTP、时钟及调度器均可替换为 fake/mock。

### P0.5（后续迭代）

- 开机自启（注册为系统服务 / LaunchAgent / Windows Service）。
- 进程守护（服务异常崩溃后自动重启）。
- Safari 预览支持（HLS 降级通道）。
- 暂停录制功能。

### 不在 P0

- 云端/服务器部署、对象存储、NAS 集中管理、远程访问或多设备同步。
- 账号体系、多用户与权限管理。
- 回放页、剪辑、转码、封面/截图、自动清理、定时预约录制。
- 绕过平台登录、付费、地域或其他访问控制；遇到受限直播时仅提示用户配置合法可用的访问凭据或告知不可录制。

## 3. 关键产品决策

| 决策 | 方案 | 原因 |
| --- | --- | --- |
| 录制位置 | 用户本机 | 符合"录像存在本地"，避免服务器带宽、存储与运维成本。 |
| 界面形态 | localhost Web（SPA），而非桌面壳 | 仍可让后台常驻，界面迭代快、跨 macOS/Windows 成本低。 |
| 并发上限 | 默认 2 路，全局配置，可配置 | 保护普通个人电脑的网络、磁盘和稳定性。 |
| 检测间隔 | 默认 60 秒（B站），抖音建议 120 秒，可配置 | 在开播时效与平台请求压力之间平衡。 |
| 断流策略 | 最多重连 3 次，5/15/45 秒退避，可配置 | 避免短暂网络波动丢失整场，也避免无限重试。 |
| 文件格式 | 优先原始流直接保存，不转码 | P0 不转码，降低 CPU 占用和失败面；中断恢复优先于兼容性。 |
| 存储保护 | 剩余空间低于 20GB 或 10%（取较大阈值）时不启动新任务 | 避免填满系统盘或生成损坏文件。 |
| 邮件去重 | 同房间、同事件 30 分钟，从首次成功发送时间开始计算 | 防止持续失败时刷屏。 |
| 预览技术 | flv.js + WebSocket-FLV | 低延迟（1-3 秒），适合直播预览场景。 |
| 预览并发 | 最多 2 路同时预览 | 与录制并发上限一致，保护本机资源。 |
| 敏感信息存储 | 操作系统 keychain（macOS Keychain / Windows Credential Manager） | 安全存储 SMTP 密码等敏感信息。 |
| 同一场判定 | 优先 roomId + streamSessionId；无 session ID 时降级为 roomId + 开播时间窗口（±10 分钟） | 避免服务重启后重复录制。 |
| 断流恢复 | 恢复原文件继续写入；流格式变化时标记当前文件完成，新建 Recording 续录 | 保证录制历史完整性。 |
| 检测失败处理 | 记录错误，下一轮调度再试，不触发重连机制 | 重连仅针对已开播后断流的情况。 |
| 停止录制 | 停用房间不打断当前录制；提供单独"停止当前录制"操作 | 避免误操作丢失已录制内容。 |
| 平台凭据 | 允许用户配置 Cookie，失效时提示重新配置 | 仅使用用户合法提供的凭据。 |
| 浏览器兼容 | Chrome/Firefox 完整支持；Safari 预览功能显示兼容性提示 | flv.js 在 Safari 上 MSE 支持不完整。 |
| 录制清晰度 | 用户可选择（原画/1080p/720p/360p），默认原画；不可用时降级 | 满足不同用户对画质和存储空间的需求。 |

## 4. 产品结构与页面规格

### 4.1 全局导航

页面包括：`首次设置`、`直播间`、`监控总览`、`录制历史`、`设置与告警`。顶部常驻显示：本地服务连接状态、录像目录可用空间、未处理告警数。通过 SSE 推送实时刷新，服务断开时明确提示，不静默显示旧数据。

### 4.2 首次设置（向导式分步表单）

首次启动必须完成以下步骤后才能启用录制：

1. 选择录像保存目录；服务校验目录存在、可写、可用空间达标。后端提供 `POST /api/settings/validate-directory` 接口。
2. 设置最大并发（默认 2）。
3. 可选配置 SMTP：主机、端口、加密方式、用户名、应用专用密码、发件人与收件人。
4. 可发送测试邮件；后端提供 `POST /api/settings/test-smtp` 接口，失败必须展示可读错误原因（连接超时、认证失败、收件人拒绝等），不能默认为"已配置成功"。
5. 保存后提示服务已开始监控，配置重启后仍有效。

### 4.3 直播间管理

每条房间包含平台、原始链接、显示名、启用状态、最近检测时间、当前状态和最近错误。添加时系统规范化链接并校验：平台是否支持、链接是否有效、是否与已有房间重复。停用不终止已在录制的文件（需在操作时明确提示）；停用后不再创建新录制。

### 4.4 监控总览

以卡片或表格展示房间状态：未开播、检测中、录制中、重连中、已完成、失败、已停用。支持"立即检测"用于诊断（REST 触发 + SSE 接收状态变更），不影响后台调度周期。失败项需要同时展示稳定错误码、用户可读说明、发生时间与是否可重试。录制中的房间提供"观看"按钮，点击后在页面内播放当前直播画面。非录制中房间不显示"观看"按钮。超过 2 路预览时提示"预览数已达上限"。录制中的房间提供"停止当前录制"按钮。

### 4.5 录制历史

按时间倒序列出录制任务：房间、平台、直播标题（获取到时）、开始/结束时间、任务状态、文件大小、文件路径、重试次数、失败原因。支持按 streamSessionId 分组展示（同一场直播被拆分为多段）或平铺展示。首期不内置播放；提供"打开所在目录"，由前端调后端 API，后端调用系统能力（macOS `open` / Windows `explorer`）完成。目录不存在或路径失效时展示可读错误。

### 4.6 设置与告警

可修改保存目录、并发、检测间隔、重试策略（重试次数、退避间隔）、空间阈值、录制清晰度（原画/1080p/720p/360p，默认原画）和邮件配置。展示目录可用空间、SMTP 最近检测结果、平台访问异常、并发已满、清晰度降级等告警；告警支持单条标记已读（`PATCH /api/alerts/:id`）+ 全部标记已读（`POST /api/alerts/read-all`），标记已读不删除录制历史中的失败原因关联。

## 5. 核心业务流程

### 5.1 自动录制流程

1. 调度器按配置间隔检查所有启用房间。
2. 平台适配器返回未开播、开播、受限或检测失败。
3. 未开播：更新最近检测时间，不创建文件或发送邮件。
4. 开播：先检查目录可写、磁盘阈值与并发数；通过后创建录制任务并启动录制器。
5. 确认文件写入成功后，任务进入"录制中"并发送开播邮件；pending 超过 30 秒未成功写入则标记 failed。
6. 正常结束：记录结束时间、大小和完整路径，状态为"已完成"，房间回到 idle。
7. 断流：进入"重连中"，按退避间隔重试，恢复原文件继续写入；达到上限后标记失败并通知。
8. 检测失败：记录错误，下一轮调度再试（不触发重连机制）。
9. 若平台流格式变化导致无法续写（录制器返回 `STREAM_FORMAT_CHANGED` 错误码），标记当前文件为已完成，新建一条 Recording 记录续录，同一 session 下的多条 Recording 共享 streamSessionId。

### 5.2 重启恢复流程

服务启动时加载本地配置和已启用房间。对未完成任务进行一致性检查，按 roomId + streamSessionId 去重；无 session ID 时降级为 roomId + 开播时间窗口（±10 分钟）。恢复后立即进入检测周期，不跳过；若房间正在直播，第一个周期即触发录制。保留可诊断的历史状态，不为同一场已存在的录制重复创建任务。若服务重启期间直播已结束，按文件是否存在且可读取判定：有文件标记 completed，无文件标记 failed。

### 5.3 通知流程

通知事件仅包括：录制成功启动、最终录制失败、空间不足。SMTP 发送失败只产生告警，不能中断录制。通知键为"房间 + 事件类型"，30 分钟去重窗口从首次成功发送通知时间开始计算。

### 5.4 页面观看直播流程

1. 用户在监控总览点击"观看"按钮。
2. 前端检查当前预览路数是否已达上限（2 路），超过则提示。
3. 前端检测浏览器类型，Safari 显示兼容性提示。
4. 前端建立 WebSocket 连接，后端通过 Node.js stream 将 FLV 数据广播到该连接。
5. 前端 flv.js 接收 FLV 流并播放。
6. 预览与录制独立：关闭预览不影响录制；录制断流时预览显示"直播已中断"并尝试重连（最多 3 次）。

## 6. 状态、数据与错误规范

### 6.1 房间状态（Room.monitorState）

`idle`（未开播）、`checking`（检测中）、`recording`（录制中）、`reconnecting`（重连中）、`failed`（失败）、`disabled`（已停用）。

说明：录制完成后房间回到 `idle`，`completed` 仅作为 Recording 的终态。房间 `failed` 后下一轮调度自动尝试检测，成功则回到 `idle`/`checking`；同时支持用户手动触发"立即检测"。

### 6.2 录制任务状态（Recording.state）

`pending`（创建后等待文件写入确认，30 秒超时则标记 failed）、`recording`（录制中）、`reconnecting`（重连中）、`completed`（已完成）、`failed`（失败）。录制任务不使用 `checking` 或 `disabled`。

### 6.3 最小数据模型

- `Room`：id、platform、url、displayName、enabled、monitorState、lastCheckedAt、lastError、createdAt、updatedAt。
- `Recording`：id、roomId、platform、streamSessionId、streamTitle、state、startedAt、endedAt、filePath、fileSizeBytes、failureReason、retryCount、quality（实际录制清晰度）。
- `Settings`：recordingDirectory、maxConcurrentRecordings、pollIntervalSeconds、retry（maxAttempts、backoffSeconds[]）、diskGuard（minFreeGB、minFreePercent）、preferredQuality（original/1080p/720p/360p，默认 original）、mail（host、port、secure、user、pass、from、to）。
- `Alert`：id、level（info/warning/error）、source、message、occurredAt、resolved。

### 6.4 错误契约

每个错误与错误事件必须至少包含：`code`、`message`、`roomId`、可选 `recordingId`、`occurredAt`、`retryable`。

错误码格式：大写蛇形，如 `ROOM_LINK_INVALID`。`retryable` 字段与前端联动，前端根据此字段展示"重试"按钮。

P0 应覆盖的错误码：

| 错误码 | 说明 |
| --- | --- |
| `ROOM_LINK_INVALID` | 链接无效 |
| `ROOM_LINK_DUPLICATE` | 链接重复 |
| `PLATFORM_ACCESS_RESTRICTED` | 平台受限 |
| `DIRECTORY_NOT_WRITABLE` | 目录不可写 |
| `DISK_SPACE_INSUFFICIENT` | 磁盘空间不足 |
| `CONCURRENT_LIMIT_REACHED` | 并发已满 |
| `RECORDING_START_FAILED` | 录制启动失败 |
| `STREAM_DISCONNECTED_RECONNECT_EXHAUSTED` | 断流重连耗尽 |
| `SMTP_SEND_FAILED` | SMTP 发送失败 |
| `SERVICE_UNAVAILABLE` | 服务不可用 |
| `NETWORK_UNAVAILABLE` | 网络不可用 |
| `RECORDING_FILE_CORRUPTED` | 录制文件写入中断/损坏 |
| `CONFIG_LOAD_FAILED` | 配置加载失败 |
| `STREAM_FORMAT_CHANGED` | 流格式变化无法续写 |
| `PREVIEW_LIMIT_REACHED` | 预览数已达上限 |
| `QUALITY_DOWNGRADED` | 指定清晰度不可用，已降级 |

## 7. 非功能要求

- **可靠性**：浏览器关闭不影响监控；服务重启后恢复已启用房间；失败可追踪而非静默吞掉。
- **安全性**：服务只绑定 `127.0.0.1`；SMTP 密码、Cookie 等敏感信息使用操作系统 keychain 存储，不回显、不写入前端，不记录到日志。
- **兼容性**：macOS 与 Windows 均支持路径选择、打开目录、服务启动和主流现代浏览器访问（Chrome/Firefox 完整支持，Safari 预览功能受限）。
- **性能**：P0 默认最多两路原始流直存 + 最多 2 路预览；录制不做转码；监控和历史页面不能因单个房间失败而不可用。
- **可观测性**：本地日志记录平台检测、录制生命周期、磁盘检查、通知结果；界面显示最近错误及发生时间。
- **合规性**：仅录制用户有权访问、保存和使用的内容；平台访问限制时应清晰告知而非规避。

## 8. 验收标准（P0）

### 核心功能

1. 可写目录通过校验，配置重启后仍存在。
2. 抖音/B站有效链接可添加；重复或失效链接被拒绝。
3. 房间可编辑、启停、删除；停用后不新建任务。
4. 未开播时持续检测，但不生成文件和邮件。
5. 开播后同一场只建立一条任务（基于 roomId + streamSessionId 去重），确认写入成功才进入录制中。
6. 正常结束有正确的开始/结束时间、路径、大小、状态，且能打开目录。
7. 断流后进入重连，按默认退避恢复或在上限后失败；文件保留已录制部分。
8. 服务重启后恢复监控，且不重复录制同一场。
9. 目录不可写或空间低于阈值时，拒绝新任务、记录原因并告警。
10. 仅在成功开录、最终失败、空间不足时发邮件；SMTP 失败不影响录制，重复事件会去重。
11. 超过并发上限时不启动额外任务，产生可见告警。
12. macOS/Windows 均可完成配置、重启恢复、打开目录和 Web 管理操作。
13. 用户可设置录制清晰度（原画/1080p/720p/360p），默认原画；指定清晰度不可用时降级到次高清晰度并产生告警。

### 界面与体验

14. 全局导航顶部常驻信息（服务连接状态、磁盘可用空间、未处理告警数）实时准确，服务断开时明确提示，不静默显示旧数据。
15. "立即检测"触发后在合理时间内返回结果，不影响后台调度周期。
16. 告警可标记已读（单条 + 全部），但不丢失录制历史中的失败原因关联。
17. 首次设置中测试邮件失败时必须展示可读错误原因。

### 页面观看直播

18. 录制中的房间可通过"观看"按钮在页面内实时观看直播画面。
19. 预览延迟 < 5 秒（正常网络），高负载下不超过 10 秒；断流后自动重连（最多 3 次）。
20. 非录制中房间不显示"观看"按钮。
21. 观看功能在 Chrome/Firefox 可正常使用，Safari 显示兼容性提示。
22. 最多 2 路同时预览，超过限制时前端提示"预览数已达上限"。

### 关闭浏览器场景

23. 录制中关闭浏览器，录制服务继续运行，文件持续写入。
24. 重新打开浏览器后状态和历史记录正确显示。

## 9. 实施阶段与依赖

### 阶段 A：方案评审 ✅ 已通过

确认本方案的范围、默认值、技术选型和平台访问策略。评审通过前暂停代码开发。

### 阶段 B：可用骨架

完成本地服务启动、配置持久化、localhost API、Web 页面骨架与 fake adapter，使用模拟平台/文件/邮件依赖跑通完整流程。

## 10. 待确认事项（已决策）

1. **文件格式**：P0 不转码，优先原始流容器直接保存。
2. **平台凭据**：允许用户配置 Cookie，失效时提示重新配置。
3. **SMTP**：首期通用 SMTP，建议使用应用专用密码。
4. **后台启动**：P0 手动启动，P0.5 纳入开机自启。
5. **停止录制语义**：停用房间不打断当前录制；提供单独"停止当前录制"操作。

## 11. 平台检测说明

### B站（Bilibili）

- 有公开的直播间状态接口，返回 `live_status` 字段（0=未开播，1=直播中，2=轮播中）。
- 无需登录即可访问，稳定性较好。
- 默认检测间隔 60 秒。

### 抖音（Douyin）

- 无公开 API，需通过抓取网页或调用内部接口获取直播状态。
- 反爬机制较严格，可能存在频率限制、验证码等风险。
- 建议检测间隔 120 秒，支持用户配置 Cookie 提高稳定性。
- Cookie 过期时（检测持续失败）提示用户重新配置。

### 通用策略

- 平台适配器设计为可替换（接口抽象 + 工厂模式），便于后续接口变更时快速更新。
- 检测失败时记录详细日志，返回"检测失败"并继续下一轮，不影响其他房间。
- 考虑 User-Agent 轮换或请求头模拟，降低被识别为机器人的风险。

## 12. 架构说明

```
┌─────────────────────────────────────────────┐
│  用户电脑（macOS / Windows）                   │
│                                              │
│  ┌──────────────────────┐                    │
│  │  录制服务（后台进程）   │ ← 常驻运行        │
│  │  - 平台检测           │                    │
│  │  - 录制管理           │                    │
│  │  - 文件写入           │                    │
│  │  - 邮件通知           │                    │
│  │  - 流转发（WS-FLV）   │                    │
│  │  - HTTP API 服务      │ ← localhost:3000   │
│  └──────────────────────┘                    │
│           ↕ REST + SSE + WebSocket            │
│  ┌──────────────────────┐                    │
│  │  浏览器（前端 SPA）    │ ← 可选，随时关闭    │
│  └──────────────────────┘                    │
└─────────────────────────────────────────────┘
```

- 录制服务是独立的 Node.js 后台进程，启动后常驻运行。
- 同时提供 HTTP API（REST + SSE）和 WebSocket 服务。
- 浏览器只是管理界面，关闭后不影响后台录制。
- 前端技术栈：Vite + React + Ant Design。
